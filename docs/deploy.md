# Deploying the backend

The backend runs as a Docker container on [Render](https://render.com) (free web service) with PostgreSQL on
[Neon](https://neon.tech) (free tier). Both are free without a credit card. Render's free service sleeps after
15 minutes without traffic, and the first request after that takes up to a minute while the JVM starts.

Everything Render needs is in the repository: [`Dockerfile`](../Dockerfile) builds the image, and the
[`render.yaml`](../render.yaml) Blueprint describes the service.

**Current deployment:** <https://todolist-server-zyck.onrender.com> (Render, Ohio) with a Neon database in
AWS us-east-2. The steps below are how it was set up, and how to set it up again from scratch.

## 1. Create the database on Neon

1. Sign up at neon.tech and create a project. Keep the Render service in the same region: `render.yaml` uses
   `ohio`, matching Neon's **AWS US East 2 (Ohio)**; change it before creating the service if you pick another one.
2. Open **Connect** and copy the connection details. Neon shows a URL like
   `postgresql://neondb_owner:secret@ep-cool-name-123456-pooler.us-east-2.aws.neon.tech/neondb?sslmode=require`.
3. Split it into the three values the server expects (the JDBC driver does not take the user and password
   inside the URL). Drop `-pooler` from the host: the server keeps its own connection pool (HikariCP), and
   Flyway migrations need a direct session rather than Neon's transaction pooler.

   | Variable | Value from the example |
   |----------|------------------------|
   | `DB_URL` | `jdbc:postgresql://ep-cool-name-123456.us-east-2.aws.neon.tech/neondb?sslmode=require` |
   | `DB_USER` | `neondb_owner` |
   | `DB_PASSWORD` | `secret` |

The schema is created by Flyway migrations when the server starts; nothing has to be run by hand.

## 2. Create the service on Render

1. Sign up at render.com with GitHub and allow access to the `ToDoList` repository.
2. **New → Blueprint**, select the repository. Render reads `render.yaml`.
3. Enter `DB_URL`, `DB_USER` and `DB_PASSWORD` from step 1. `JWT_SECRET` is generated by Render;
   `APP_ENV=production` and `TRUST_PROXY=true` come from the Blueprint.
4. Apply. The first build takes several minutes. When it is done, the service URL is shown on the dashboard,
   for example `https://todolist-server.onrender.com`.
5. Check it: `curl https://todolist-server.onrender.com/health` returns `{"status":"UP"}`.

From then on every push to `main` is deployed automatically once the CI checks pass
(`autoDeployTrigger: checksPass`).

## 3. Point the release apps at the server

Render adds a suffix when the service name is taken, so use the exact URL from the dashboard:

- Android: `todolist.releaseApiBaseUrl=https://todolist-server-zyck.onrender.com` in `gradle.properties`.
- iOS: `API_BASE_URL[config=Release]=https:/$()/todolist-server-zyck.onrender.com` in
  `app/iosApp/Configuration/Config.xcconfig`.

Debug builds keep using the local server.

## Production configuration

| Variable | Required | Purpose |
|----------|----------|---------|
| `APP_ENV` | yes (`production`, set in the image) | Enables production checks |
| `JWT_SECRET` | yes | HS256 signing key, at least 32 characters; the server refuses to start without it |
| `DB_URL`, `DB_USER`, `DB_PASSWORD` | yes | PostgreSQL connection |
| `TRUST_PROXY` | behind a proxy | Take the client IP from `X-Forwarded-For` for rate limiting |
| `AUTH_RATE_LIMIT_PER_MINUTE` | no (20) | Requests per client IP per minute to `/api/v1/auth/*` |
| `GOOGLE_CLIENT_IDS` | no (project clients) | Accepted Google ID token audiences |
| `METRICS_TOKEN` | no | Enables Prometheus metrics at `/metrics`, scraped with `Authorization: Bearer <token>` |

## Operations

| Endpoint | Purpose |
|----------|---------|
| `GET /health` | Liveness: the process is up |
| `GET /health/ready` | Readiness: the database answers; Render's health check uses it, so a deploy that cannot reach the database never replaces a working instance |
| `GET /metrics` | Prometheus metrics (request timings by route and status, JVM memory, GC, threads); only with `METRICS_TOKEN` in production |

Logs in the Docker image are JSON, one object per line, with the request's `call-id` (also returned to clients
as `X-Request-Id`) as a field, so a single request can be followed through Render's log search. Local runs keep the
plain text format.

Changing `JWT_SECRET` signs everyone out: existing access tokens stop validating.

## Running the image locally

```bash
docker build -t todolist-server .
docker run --rm -p 8080:8080 -e JWT_SECRET=$(openssl rand -base64 32) \
  -e DB_URL=jdbc:postgresql://host.docker.internal:5434/todolist -e DB_USER=todolist -e DB_PASSWORD=todolist \
  todolist-server
```
